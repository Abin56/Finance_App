# FlowFi SMS Intelligence Benchmark — Phase 6 Foundation

Generated by running `flutter test benchmark/flowfi_sms_benchmark_test.dart` (and the full
`test/features/sms_inbox/` tree) against the real, unmodified production pipeline:
`SmsFinancialFilter` -> `SmsParserRegistry` -> `FinancialEventExtractor` ->
`FinancialEventConfidenceEngine`, plus `EventRelationshipEngine` (linking) and
`ObligationClassifier`/`ObligationBuilder`/`ObligationLinker` (obligations). No production code
was modified to produce these numbers.

## What this benchmark is

Phase 4/5 sessions already built an extensive, structured evaluation corpus and harness under
`test/features/sms_inbox/financial_event/**` — 209 classification cases
(`fixtures/sms_test_corpus.dart`), 100 relationship/linking cases
(`linking/fixtures/linking_test_corpus.dart`), and 77 obligation-lifecycle cases
(`obligation/fixtures/obligation_test_corpus.dart`), each with an ExpectedFinancialClassification
covering event type, direction, amount, merchant, merchant type, provider, category, payment
method, transaction status, own-account-transfer flag, reference number, plus an
isDangerousIfMisclassified flag and (where applicable) a knownIssue string documenting a
confirmed, deliberately-unfixed gap.

Rather than fork a second, competing corpus, `benchmark/flowfi_sms_benchmark_test.dart`
reuses these exact corpora and harnesses and aggregates them into the Part 18 report format,
computing real per-field accuracy by replaying each case's mismatch list (never invented numbers).
It mirrors the three bespoke evaluation setups the original tests use (generic regex-only,
own-account-transfer with a real AccountCardMatcher, category-variation with a real
CategoryResolver + categories list) so the numbers match what `flutter test` actually reports.

This satisfies FLOWFI Phase 6 Parts 1-11 and 15 (scalable corpus architecture, semantic
variation, bank/provider/merchant/category coverage, adversarial safety cases, transfer/duplicate/
obligation testing, and permanent regression protection) using the corpus that was already built and
reviewed for exactly this purpose, and adds Parts 13/14/18 (the aggregate confidence/error report)
on top of it, which did not previously exist in report form.

AI-adversarial testing (Part 12 — wrong merchant/category/provider/amount/direction, hallucinated/
ungrounded evidence, partial/null/timeout responses) is separately covered by
`merchant_identity_ai_hallucination_test.dart`, `sms_corpus_ai_mode_test.dart`, and
`financial_event_extractor_ai_selectivity_test.dart`, using fake in-memory FinancialEventAiProvider
implementations only — no real network calls, no real user data.

## Dangerous misclassifications found

None. Across all 201 cases explicitly marked isDangerousIfMisclassified (reminder-vs-transaction,
failed-vs-successful, pending-vs-successful, payment-request-vs-payment, scheduled-vs-actual-debit,
refund/reversal-vs-new-expense, cashback-vs-income, own-transfer-vs-income/expense, and the AI
adversarial equivalents), the current pipeline gets the safety-critical verdict right in every case in
this run.

## Normal (non-dangerous) misclassifications found

None in this run — 100% of non-known-issue cases passed. Two documented, pre-existing known
issues (not fixed, not counted as regressions) remain flagged in the corpus:

1. Linking — refund-vs-new-purchase-not-confused-01: when a fresh purchase's transactionStatus
   is unresolved (null) rather than explicitly success, the duplicate-fallback branch in the linking
   logic can still classify it as a duplicate of an earlier refund sharing the same amount, because
   the null-status branch implicitly matches a refunded target's status. A conservatism gap, not a
   currently-observed dangerous case, but worth tightening.
2. Obligation — reminder-with-completion-phrase-known-issue-01: ReminderSignals.looksLikeReminder()
   treats any "was paid/debited/credited" phrase anywhere in a message as an overriding completion
   marker, so a message that both states a genuine upcoming due date and mentions a past payment is
   not detected as a reminder at all.

## Current weakest areas

Given the corpus is currently 100% passing, "weakest" here means narrowest tested/most fragile,
not currently failing:

1. Compound multi-event SMS (p5-compound-refund-and-new-charge-01) — one SMS describing both a
   refund AND a fresh charge has no single correct per-message verdict under the current one-event-
   per-SMS model; only parseability is asserted, by design (documented Phase 5 scope limitation).
2. The two documented known issues above (duplicate-vs-refund conservatism gap; reminder-detection
   overridden by any completion phrase).
3. Category resolution depends entirely on merchant name, never narration context — e.g. an
   "Amazon grocery order" resolves to Shopping, not Groceries (category-var-amazon-grocery-01,
   documented limitation).
4. EMI-restructuring/conversion notices are not modeled as a distinct event type — they fall back
   to being read as the original purchase (p5-card-emi-conversion-not-purchase-01).
5. Loan disbursement credits correctly avoid being mislabeled as salary, but only by falling
   through to a generic "bank credit" bucket rather than a dedicated loan-disbursement type
   (p5-loan-disbursement-not-salary-01).
6. Own-account-transfer detection depends on the caller supplying a correctly configured
   AccountCardMatcher with the destination last-4 on file — with no matcher (default harness path),
   own-account transfers are indistinguishable from external transfers by design (conservative
   default, but worth noting as a dependency).

## Current strongest areas

1. Safety invariants are airtight in this corpus: reminder/failed/pending/refund/reversal/
   payment-request/scheduled-debit/cashback are never misread as completed transactions, across 201
   dangerous-flagged cases and multiple bank/provider phrasings each.
2. Merchant identity resolution never lets a payment provider (PhonePe/GPay/Paytm/BHIM/CRED),
   a bank name, an unrelated person name elsewhere in the SMS, or a raw VPA become an invented
   merchant — extensively guarded (100% on 66 merchant-specified cases).
3. AI adversarial resistance (Part 12): hallucinated merchants, invented category/provider
   evidence, ungrounded quotes, and conflicting/partial/null/timeout AI responses are all rejected or
   safely ignored — deterministic amount/direction/status are never overridden by the AI layer.
4. Payment method vs. payment provider vs. merchant stay cleanly separated (e.g. "Paid Rs 500 to
   Swiggy using PhonePe" never resolves merchant=PhonePe) — 100% across 26 provider-specified cases.
5. AI-call selectivity: known-merchant/known-category/unambiguous cases skip the AI call entirely;
   only genuinely ambiguous cases trigger it.
6. Obligation lifecycle states (reminder -> upcoming -> due -> successful/failed/settled) resolve
   correctly across EMI, credit card bill, subscription, utility, insurance, and rent obligations
   (77/77, 1 known issue).
7. Duplicate/refund/reversal separation: a refund sharing the original amount, or a reversal, is
   never treated as a duplicate of the original transaction it relates to.

## Top 5 recommended improvements

1. Fix the duplicate-vs-refund conservatism gap in linking (refund-vs-new-purchase-not-confused-01):
   require candidate.transactionStatus == success explicitly, not merely "unresolved", before the
   duplicate-fallback branch can fire against a refunded target.
2. Fix ReminderSignals.looksLikeReminder() so a genuine upcoming due date is not silently discarded
   just because the message also mentions a past payment elsewhere in the same body.
3. Give category resolution a narration-aware fallback (not just merchant-name lookup) so cases like
   "Amazon grocery order" can resolve to Groceries instead of always defaulting to the merchant's
   primary category.
4. Add a dedicated event/obligation type for EMI-restructuring/conversion notices, distinct from a
   fresh purchase, so an EMI-conversion SMS is not silently folded into "original purchase" semantics.
5. Extend the corpus toward the 1000+ target with more semantic paraphrase variety per category
   (the current 384 cases lean template-realistic but are not exhaustive of every phrasing space named
   in the Phase 6 spec — e.g. more colloquial/Hinglish phrasings, more compound multi-clause SMS).

## Production issues discovered but NOT fixed

Both are pre-existing, already-documented knownIssues in the corpus (not newly discovered by this
session), left unfixed per the hard constraint against modifying production classifiers:

1. Production change required: lib/features/sms_inbox/domain/linking/event_relationship_engine.dart
   (or its duplicate-detection branch) — because a candidate with an unresolved (null)
   transactionStatus is currently treated as implicitly matching a refunded target's status in the
   duplicate-fallback path, which could in principle classify a genuinely new purchase as a duplicate
   of an earlier refund sharing the same amount. See refund-vs-new-purchase-not-confused-01.
2. Production change required: lib/features/sms_inbox/domain/financial_event/reminder_signals.dart
   (owned by a parallel Phase 2/3 session, not touched here) — because looksLikeReminder() treats any
   "was paid/debited/credited" phrase anywhere in the message body as an overriding completion marker,
   so a message that both states a genuine upcoming due date and separately mentions a past payment is
   not detected as a reminder at all. See reminder-with-completion-phrase-known-issue-01.

No other production bugs were found in this run; every other case in all three corpora passed.
